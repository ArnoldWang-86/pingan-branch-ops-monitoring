## 一、我为什么做这个项目，以及为什么这么设计

我在看平安银行上海自贸分行运营培训生这个岗位的 JD 时，把它拆成了三件事：

1. 「了解各项业务与产品、运营业务板块，熟悉相关业务流程」→ 需要**懂运营指标**；
2. 「树立风险合规意识」→ 需要能**分辨什么是真风险、什么是数据问题**；
3. 「精通银行全领域业务的综合金融业务精英」→ 需要能**从数据走到动作**。

我原有的作品集偏互联网内容与用户分析，缺一块**银行运营**的东西。所以补了这个项目。

但真开始做就撞上第一个问题：**网点级的运营微观数据，公开渠道根本拿不到。**

我实际去检索过：人民银行《支付体系运行总体情况》17 份报告全文里没有「营业网点数量」
「柜面业务量」「平均等候时长」这类口径；「助农取款服务点」在 17 份报告里检索命中 0 次
（该口径已废止）；金融监管总局的「商业银行主要监管指标情况表」页面是 JS 动态渲染，
抓不到表格。这些指标属于各行内部经营数据。

于是我把项目拆成两层，并且**在报告里、看板上、简历里都明确标注**：

- **真实公开数据层**：28 个来源、601 条已核实指标。用来设定模拟数据的「水位与波动范围」。
- **模拟数据层**：网点级日运营指标，20 家网点 × 90 天 = 1,800 条。
  用来验证「指标监控 + 异常预警」这套**方法本身**。

**这个取舍我必须写清楚**：模拟数据不代表任何真实银行的经营情况。
它的价值在于，我可以往里面**注入已知的异常**，从而第一次能真正回答
「你的预警系统到底准不准、会不会天天误报」——而不是只交一张「看起来有异常」的图。

## 二、一个与本岗位直接相关的真实发现

平安银行自 2022 年报起，每一期定期报告都**单独列示「上海自贸试验区分行」**，
我把 6 期数据都取了出来：

| 报告期 | 资产规模（亿元） | 员工人数（人） |
|---|---:|---:|
| 2022A | 685.12 | 159 |
| 2023H | 837.82 | 157 |
| 2023A | 780.16 | 153 |
| 2024H | 828.51 | 157 |
| 2024A | 883.66 | 158 |
| 2025A | 1085.26 | 152 |

四年资产 +58.4%，员工从 159 人减到 152 人。

这件事给了我做这个项目的具体问题意识：**当业务量在涨、人手不涨甚至减少时，
运营管理靠什么？** 靠的是把「单位产能」盯住、把窗口调度做对、
并且——这点最容易被忽视——**不要把系统的错误算到网点头上**。
后面整份报告的主线就是这个。

## 三、指标体系：为什么是这四个维度

我没有把能算的指标都算上，而是按运营管理的四个决策场景分层，每层回答一个具体问题：

| 维度 | 回答的问题 | 核心指标 |
|---|---|---|
| 效率 | 客户等多久？窗口够不够？ | 柜面业务量、平均/最长等候时长、窗口产能饱和度、单窗口业务量 |
| 服务 | 客户满意吗？渠道分流有效吗？ | 电子渠道分流率、智能设备占比、客户满意度、投诉率（每万笔） |
| 成本 | 单位业务的运营成本合理吗？ | 运营成本收入比、人均业务量 |
| 风险 | 操作合规吗？差错可控吗？ | 业务差错率、事后监督复核率、差错率周度趋势 |

**一条口径纪律**：所有比率类指标在数据层只落「分子」和「分母」，
比率在查询/分析时才计算。这是我在另一个项目里踩过坑之后定下来的规矩——
当时清洗层与分析层各写了一套分类词典，两套数永远对不上，排查了半天。
所以这次我在 `dwd_branch_ops_daily` 里把分子分母都留着，
下游想换口径可以自己重算，不会出现「同一指标两个值」。

## 四、模拟数据是怎么造的

我没有随手编随机数，而是让数据尽量符合真实运营的物理关系。

### 4.1 等候时长由排队论关系推导，而不是独立编一个数

```
产能占用率 u = 柜面业务量 × 单笔服务时长 / (开放窗口数 × 日有效服务时长)
平均等候   = 系数 × u / (1 - u)^0.85
```

这样处理带来一个重要的性质：**等候时长与业务量、窗口数是联动的**。
注入「产能不足」时，业务量涨 35%，等候时长自然会被推到高位，
而不是我手工把等候时长也乘一个倍数。这让我后面能判断
「等候时长涨是因为真的忙，还是因为别的原因」。

同理，**口径调整只改变上报的业务量，不改变真实排队压力**——
所以等候时长不跟着变。这正是区分「口径差异」与「真实风险」的关键依据
（详见第六节）。

### 4.2 差错与投诉用泊松计数，而不是乘倍数

业务差错和客户投诉是**低频计数事件**。第一版我犯了个错：把「投诉率乘 4 倍」
当作异常注入。结果那个网点的投诉基线接近 0，乘 4 之后期望值仍不足 1 笔，
泊松抽样长期取到 0，**这个异常实际上从未发生**。

这件事让我意识到：低频计数指标必须用绝对件数来表述异常
（「每日新增投诉 5~9 笔」），而不是用相对倍数。

### 4.3 三道质量闸门

1. **锚点单位校验**：从公开数据取参数时，只接受单位为 `%` 或纯比例（0~1）的值。
   因为人行报告里「离柜交易总额 2626.80 万亿元」这类指标名里也含关键词，
   但它是**绝对量**。一旦被当成比率取用，会把分流率设到 0.86 这种离谱水平，
   整个模拟数据集就失真了。这个 bug 真的发生过一次。
2. **注入自检** `validate_injections()`：每个注入都必须在生成数据里
   **可观测到**（效应量达标，且对照指标保持平稳），否则直接报错退出。
3. **随机种子固定**：`--seed 20260901`，结果完全可复现。

> 自检这道闸门救了两次：一次是上面说的投诉注入从未生效；
> 一次是我把分流率锚点设错，导致「产能不足」注入后等候时长几乎不变（+1.6%），
> 自检直接把这两例标成 FAIL。没有这道闸门，我的查全率会是一个自欺欺人的数字。

## 五、异常检测：为什么用三路方法，以及基线为什么要按星期几对齐

### 5.1 三路互补

| 方法 | 擅长的 | 抓不到的 |
|---|---|---|
| 横截面稳健检测（Median + 1.4826×MAD） | 单日突发偏离 | 「每天高一点」的缓慢漂移 |
| 单网点 EWMA 控制图 | 缓慢漂移（对照自身历史） | 全行同步变化 |
| STL 周期分解（period=7, robust） | 剥离周内效应后看趋势与残差 | 需要足够历史长度 |

**为什么用 MAD 而不是 3σ**：运营数据里有**真实的**极端值（设备故障、营销活动）。
标准差会被这些值撑大，导致真正的异常反而落进 3σ 以内检不出来。
MAD 对极端值不敏感，1.4826 是把 MAD 校正到与正态标准差同尺度的常数。

### 5.2 最关键的一处修正：基线必须按星期几对齐

这是本项目返工最多的地方，值得完整讲一遍。

**第一版做法**：基线用「前 7 日滚动均值」。

**结果**：注入 7 例已知异常，只检出 4 例。

**排查过程**：漏掉的 3 例全部是同一个原因。看数据发现，
**周日业务量只有工作日的约三分之一**（`WEEKDAY_FACTOR` 里周日是 0.34）。
于是每个周日，业务量相对 7 日滚动均值都显示约 -65%。

这带来两个后果，第二个更致命：

1. 每周固定产生一次假异常；
2. **更严重的是**，我为了压制这种假异常设了「持续性门槛」，
   真实的缓慢异常因为被周期性假信号打断，**永远达不到持续性门槛，反而被滤掉了**。
   换句话说：假异常把真异常挤出去了。

**修正**：基线改成「**同星期几中位数**」——对每个网点、每个星期几，
取此前 4 个同星期几观测的中位数作为基线。它天然剥离周内效应，也不需要拟合季节模型。

**效果**：7 例全部检出。

> 这个教训我一直记着：**做异常检测，先把数据的固有周期结构搞清楚，
> 否则你不是在检测异常，而是在检测星期几。**

### 5.3 预警分级：幅度 × 持续性 × 方法一致性

只看偏离幅度会导致两种错误并存：缓慢漂移（单日幅度小）永远报不出来，
而正常波动的单日越线又天天在报。所以：

```
severity_score = 幅度 × 持续性系数 × 方法一致性 × 10

  幅度        ：各指标相对同星期几基线的最大偏离，封顶 3.0
                （封顶是为了防止「字段单位错误」那种 60 倍量级
                 把严重度打到几百，失去区分度）
  持续性系数  ：7 日内越线 ≥5 天 → 1.0；≥3 天 → 0.8；否则 0.35
                口径调整这类台阶式变化，用「台阶持续天数」参与计算
  方法一致性  ：三路方法同时命中时加成，最多 +30%
```

这里有个我纠结过的设计选择：**「台阶检测」该不该豁免持续性门槛？**

一开始我让它豁免（台阶本身就是持续性的证据）。结果台阶状态一旦触发就连续多日报警，
预警量从 202 条涨到 570 条，注入期外预警比例升到 25%——噪音太多。
后来改成**按天累计**：把「近 7 日内被判定为台阶的天数」也作为持续性来源之一。
这样既保留了真实证据，又不会放大成噪声。

## 六、最有价值的部分：把「数据错误 / 口径差异 / 真实风险」分开

单一指标跳变**无法**定性。这三类异常都会让指标跳变，
但处置方式完全相反：

- **数据错误** → 应该修系统，**不该问责网点**
- **口径差异** → 应该回算基线，**不该问责网点**
- **真实风险** → 才需要运营干预

所以必须做**指标间交叉校验**。以下三条判据是本项目真正能把三类分开的规则，
**每一条都是被数据打回来之后才定下来的**：

| 异常性质 | 专属特征（指标间关系） | 为什么这条能成立 |
|---|---|---|
| 数据错误·字段单位 | 等候时长量级放大 **8 倍以上**，业务量与差错率全部正常 | 业务运营不可能出现这种量级，只可能是字段单位（分钟/秒）问题 |
| 数据错误·批量重跑 | 业务量虚高，但**成本收入比反而下降** | 成本率的分母是业务量，分母虚高则比率被动下降——指标之间不自洽 |
| 口径差异 | 业务量**台阶式**下降，等候时长**不跟着降** | 若客户真的变少，等候时长必然下降；等候不变说明是统计口径变了 |
| 真实风险·渠道故障 | 电子渠道分流率骤降 + 柜面量与等候同步上升 | 分流率下降是渠道故障的专属特征 |
| 真实风险·产能不足 | 业务量与等候时长**同步**持续走高 | 排队论关系成立，说明是真的忙 |
| 真实风险·操作风险 | **周度**差错率显著抬升 | 差错是低频计数，日粒度信噪比太低 |

**规则顺序即优先级**，这一点踩过坑：我一开始把「字段单位错误」排在「渠道故障」前面。
结果自助设备故障时，等候时长也会被放大（1.35 倍），
被误判成了字段单位问题。调整顺序后正常。

### 6.1 为什么差错率必须按周看

差错是低频计数事件。单日差错率的分母只有几十到几百笔业务，
分子是 0~2 笔，日粒度的偏离几乎全是抽样噪声。
改成「7 天累计差错数 / 7 天累计业务量」之后，
「差错率缓慢漂移」这一类异常才稳定可识别。

### 6.2 评估口径的一个选择，我把它写出来而不是藏起来

**但这里要给两个数，而不是一个。** 评估脚本先按 3 大类归并再比对
（数据错误 / 口径差异 / 真实风险），该口径下是 7/7；
若按**细分类型**严格比对，则有一例判错：

> `error_drift`（SH011 新人轮换致差错率漂移）应判为「操作风险」，
> 实际在整个窗口内只产出过「服务风险」预警。
> 原因是该网点差错率与投诉率同时抬升，而判定规则中服务风险条件先满足，
> 首报按投诉归因，此后也一直沿这条路走。

**大类没错、细类错了。只报 7/7 会掩盖这一点**，所以两个数都列出来。
这也说明：我的成因判定在「同一大类内多个症状并发」时会选错细分类型，
这是当前规则式判定的真实短板。

「性质判定正确」统计的是**整个异常窗口内**是否判出正确性质，
而不是**首条预警**的性质。

原因：像「差错率缓慢漂移」这类异常，窗口前期可能先被别的指标触发
（在该网点投诉基线恰为 0 的情况下尤其明显），随着漂移累积，正确性质才浮现。
只看首条会把这种正常收敛过程记成错判。

这是评估口径的选择，换一种口径数字会变。所以我把它写在报告里，
而不是挑一个好看的口径然后不提。每例的「首次判对时间」也落在
`03_异常检出评估.csv` 的 `cause_correct_on` 字段里，可以人工复核。

## 七、结果

| 指标 | 结果 |
|---|---|
| 注入已知异常 | 7 例 |
| 检出 | 7 例（**查全率 100%**） |
| 性质判定正确（3 大类） | 7 例（**100%**） |
| 性质判定正确（细分类型） | 6 例（**85.7%**） |
| 预警总数 | 171 条 |
| 注入期外预警 | 135 条，占全部网点日的 7.50% |

**关于 7.50% 这个数字，必须说清楚它的口径**：
它是「注入窗口外预警数 / 全部网点日数」，是误报率的**上限**。
因为真实运营中本来就存在大量未被登记的波动（营销活动、临时调休、社区事件），
它们不算假警报，但在这个口径下全部被计入。

**而且**：7 例注入都是我设计的、单一成因的、效应量明确的异常。
真实世界很少这么干净。所以查全率 100% **不代表**在真实数据上也能达到。

## 八、四次自我纠错（我认为这比结果本身更值得写）

### 纠错一：投诉异常从未发生

第一版模拟器里，「投诉率升至基线 6 倍」这个注入实际上**从未生效**：
该网点投诉基线接近 0，乘 6 后期望值仍不足 1 笔，泊松抽样长期取到 0。

如果没发现，我的检测算法会去「检出」一个不存在的异常，
评估结果就是假的。发现之后我加了 `validate_injections()` 自检，
并且把低频计数指标的异常表述改为**绝对件数**。

### 纠错二：周内效应把真异常挤掉了

第一版用 7 日滚动均值做基线，7 例只检出 4 例。
排查发现是周日业务量骤降造成的周期性假信号，
它既产生假异常，又通过持续性门槛把真异常滤掉。改为同星期几基线后 7/7。

### 纠错三：一个更隐蔽的锚点错误

从公开数据取参数时，我最初的关键词匹配把
「离柜交易总额 2626.80 万亿元」当成了分流率。它是绝对量，不是比率。
这会把分流率设到 0.86，进而让「产能不足」注入几乎不产生效果（等候 +1.6%）。
自检把它标成 FAIL 之后我才发现。修正方式是**校验单位**：
只接受 `%` 或纯比例值。

### 纠错四：我造出了一个「长期超负荷」的网点

这一条是收尾复核时才发现的，也是四条里最基础的一条。

自贸区分行营业部在我的参数表里被设为**业务量档位 2.60、窗口档位 1.60**。
结果它的窗口产能饱和度长期停在 **124%**、日均等候时长 **215 分钟**——
而它**并没有被注入任何异常**。

也就是说，我在「正常网点」上放了一个日均等候 3.5 小时的营业部。
这不是运营现实，是我的**参数标定错误**（业务量需求与窗口供给不匹配）。
它还带来一个连带污染：23 条「平均等候 400 分钟以上」的误报全部堆在这个网点上，
把成因而定性的分布带偏了。

修正方式：调整各网点类型的业务量与窗口档位，使其在最高峰日的饱和度落在
0.6~0.9 区间——**常态网点不应长期满负荷，只有注入了「产能不足」的网点才该被推到高位**。
修正后该网点饱和度 81%、等候 15.1 分钟，全部 20 家网点的饱和度回到 20%~99%。

同时我顺手修掉了一个**判据脆弱性**：原先「字段单位错误」用
`等候时长 > 同星期几基线 × 8` 这种**纯相对**判据。当网点基线本身偏高时
（例如 52 分钟），417 分钟这种「平均等候 7 小时」的荒谬值只到基线的 8 倍出头，就抓不住。
改为「绝对量级不可信（>180 分钟）+ 相对基线或**全行中位数**的倍数」三重条件后，
这类值被正确归入数据错误，而不是滞留在「待定」（待定预警从 99 条降到 78 条）。

> 这两处的共同教训：**先确认数据本身是否合理，再去评价模型好不好。**
> 如果我只盯着「检出率 7/7」这个指标，是发现不了「有个网点在正常状态下
> 就排了 3.5 小时队」的——因为检测器没报错，它只是忠实地反映了错的输入。

## 九、我知道的局限

1. **网点级微观数据的公开来源确实不存在。** 我检索了人行 17 份报告全文、
   监管总局指标页、银行业协会服务报告，共 11 项指标确认无公开来源，
   全部记为 `null`，**没有用任何数字去填**。
2. **模拟数据只能锚定量级与波动范围，不能锚定个体数值。**
   所有网点级具体数字不可用于推断任何真实银行。
3. **注入异常是我设计的**，形态比真实异常更干净、更典型。
   查全率 100% 不代表真实场景表现。
4. **阈值是在这个数据集上调出来的**，存在过拟合风险，换数据需重新标定。
5. **节假日效应没有单独建模**，只处理了周内效应。
6. **SQL 层与 Python 层的稳健离散度口径不完全一致**：
   MySQL 没有 MEDIAN 聚合函数，SQL 层用「平均绝对偏差」近似，
   Python 层用真 MAD。两者都稳健但数值不完全相等，已在注释中标注。
7. **人行报告 2025Q1 起改版**，删除了「人均持有银行卡」「每万人拥有 ATM」
   等明细项。这是「报告不再披露」，不是「数据缺失」，
   做长时序时两者处理方式完全不同。

## 十、如果重做一次

1. **基线口径一开始就按「同星期几 + 节假日」分层**，而不是等漏检了才回头改。
2. **注入更多复合异常**（如口径调整叠加人员变动），现在 7 例都是单一成因。
3. **给预警加处置闭环字段**（已确认 / 已处置 / 误报），
   这样可以用运营反馈来修正阈值，而不是一直靠我手工标定。
4. **低频指标直接以周为最小分析单位**，不要先按日算再聚合——
   中间那一步的噪声会污染结论。

## 十二、工程上踩到的三个小坑（不影响结论，但值得记下来）

这三条都不是分析方法问题，而是「Windows 中文环境 + Office 文档」的工程问题。
我把它写下来，是因为下次做同类项目一定会再遇到。

### 12.1 批处理文件里的中文会让 cmd 语法解析失败

`cmd.exe` 是按**控制台代码页**解析 `.bat` 文件的。如果 `.bat` 是 UTF-8 且含中文，
在某些机器上会直接报 `'xx' is not recognized as an internal or external command`，
而且这个错误发生在 `chcp 65001` 生效之前，所以加 `chcp` 也救不回来。

试过存成 GBK 也不行——这台机器的 cmd 实际代码页并不是 936。
最终做法：**`run_all.bat` 保持纯 ASCII**，中文说明放在 README 与 `run_all.ps1` 里。

### 12.2 不要把中文文件名作为参数传给 Python

在批处理里写 `python md2docx.py results\运营建议报告.md ...`，
参数经过代码页转换后到达 Python 时已经损坏（实测文件名里全是 `\ufffd`，
报 `FileNotFoundError`）。改成让脚本自己在目录里发现文件
（`md2docx.py --all` 的 `build_all()`），就绕开了这一层。

### 12.3 Word 表格会撑出版心宽度

一开始我只设了 `table.columns[i].width`，以为就够了。实际渲染出来表格右侧被裁切。
原因是 Word/LibreOffice 的**单元格默认左右内边距（各约 108 twips）是在列宽之外额外占位的**，
列宽之和等于版心宽度时，加内边距就会溢出。修法是两步：
用 `w:tblW` 固定表宽、用 `w:tblCellMar` 显式把内边距设小（各 60 twips）。

> 这里有个方法论教训值得单独说：**我是靠渲染出图才发现的，光看 XML 看不出来。**
> 生成 Office 文档不能只做结构校验（ZIP/XML 完整性），
> 必须真的渲染一遍、量一下文字坐标有没有越界。
