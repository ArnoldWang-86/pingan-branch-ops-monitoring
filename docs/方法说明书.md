## 零、先用三分钟搞懂这个项目在做什么

### 一句话版本

**我给 20 家银行网点造了 90 天的运营数据，故意埋进 7 个"已知的毛病"，然后写程序去自动找出来——并判断每个毛病到底是"真问题""录入错误"还是"统计口径变了"。7 个全部找出来了。**

### 一个类比（不懂银行也能懂）

把它想成**给银行网点做体检**：

| 现实中的体检 | 这个项目 |
|---|---|
| 量血压、测心率、验血 | 记录每天的业务量、客户等候时长、差错笔数、投诉笔数 |
| 判断"这个指标是不是不正常" | 跟这家网点**以往同一个星期几**的水平比（不是跟昨天比） |
| 血压计坏了，读数 300 | 判断出"这是仪器坏了"，**不是**病人真有病 |
| 换了个新血压计，刻度不一样 | 判断出"这是换了标准"，也不是病人变差 |
| 真的血压高 | 判断出"这是真问题，要吃药" |
| 医生写体检报告 | 生成运营建议报告 + 看板 + 可用自然语言提问的 Agent |

**这里最关键的是中间三行的区别。** 很多监控系统只会喊"异常！异常！"，
但把血压计坏了的读数也当成病人有病去治，医生就没人信了。
**这个项目最核心的工作，就是把这三类区分开。**

### 为什么必须自己造数据

因为**银行网点每天的真实运营数据是内部经营数据，公开渠道拿不到**。

我认真找过了（不是随口说"找不到"）：人民银行《支付体系运行总体情况》共 17 份报告，
全文里**没有**"营业网点数量""柜面业务量""平均等候时长"这类口径；
"助农取款服务点"在 17 份报告里检索**命中 0 次**（这个口径已经废止）；
金融监管总局的"商业银行主要监管指标情况表"是网页动态渲染的，抓不到表格。

一共 **11 项指标我确认不存在公开来源，全部诚实地记为"空值"（null），没有编任何数字去填。**

### 所以数据分两层，这一点必须说清楚

| | 是什么 | 有多少 | 用来干什么 |
|---|---|---|---|
| **① 真实公开数据** | 别人公开披露的真实数字，每条都能追溯到原文 | 28 个来源、**601 条已核实指标** | 给模拟数据定"正常应该是什么量级" |
| **② 模拟数据** | 我按真实量级造出来的网点级数据 | 20 家网点 × 90 天 = **1,800 条** | 验证这套监控方法**本身**好不好用 |

**必须写在最显眼处的边界**：
模拟数据只保证"量级和波动范围像真的"，**每一个具体的网点数字都不代表任何真实银行的经营情况**。

**为什么一定要用模拟数据？** 因为只有自己造的数据，我才能**故意埋进已知的毛病**，
从而回答一个关键问题：**"你这套预警到底准不准、会不会天天误报？"**
如果只用真实数据，我永远无法证明这一点——我只能交出一张"看起来有异常"的图，而说不出它对不对。

### 最终结果一览

| 指标 | 结果 |
|---|---|
| 埋进去的已知毛病 | 7 个 |
| 找出来 | **7 个全找到（查全率 100%）** |
| 性质判断正确（3 大类） | **7/7** |
| 性质判断正确（细分类型） | **6/7（85.7%）** |
| 总共报警 | 171 次 |
| 其中落在"埋雷期间" | 36 次 |
| 不在埋雷期间的报警 | 135 次，占全部网点日 **7.50%**（这是误报率的**上限**，见第十节解释） |

## 一、名词解释：看懂这份文档需要的所有术语

### 1.1 银行业务术语

**网点 / 支行 / 分行营业部**
银行开门做生意的实体门店。一级管一级：总行 → 分行 → 支行。
"营业部"通常是一个分行里规模最大、业务最全的那家门店。

**柜面业务**
客户**到人工柜台**办的业务，比如存取大额现金、开卡、挂失、对公开户。
与之相对的是**电子渠道**（手机银行、网上银行）和**智能设备**（网点里的自助机具）。

**柜面业务量**
一天里，一家网点通过人工柜台办了多少笔业务。这是本项目最基础的指标。

**平均等候时长**
客户取了号之后，等多久才轮到被叫号。单位是分钟。
这是客户体验最直接的痛点指标。

**窗口 / 开放窗口数**
柜台有几个。开 7 个窗口就是同时能服务 7 位客户。
窗口数越多，客户等得越短——但人力成本也越高。

**窗口产能饱和度**
> 意思：窗口到底有多忙。**100% 表示满负荷**，超过 100% 表示排不过来了。

计算方式：`实际业务量 ÷ 窗口数 ÷ 理论单窗口产能`。
比如一个窗口理论上 8 小时能办 50 笔，实际办了 45 笔，饱和度就是 90%。

**业务差错**
柜员办业务时出的错，比如金额录错、凭证不全、签名缺失。
银行有**事后监督**环节专门复核，复核出的问题会记成差错。

**业务差错率**
> 意思：办 100 笔业务，有几笔出了问题。

计算方式：`差错笔数 ÷ 柜面业务量`。
本项目里这个数字大约是 **0.45%**（一千笔里四五笔），与银行业公开区间一致。

**投诉率（每万笔）**
> 意思：每办 1 万笔业务，收到几个客户投诉。

单位是"笔/万笔"。注意**不是百分比**，因为投诉相对业务量非常稀少。

**电子渠道分流率**
> 意思：所有业务里，有多少比例是通过手机银行、网银、自助机具办的，而不是去柜台。

计算方式：`(智能设备 + 移动端业务量) ÷ 总业务量`。
本项目实测约 **73%**，即四分之三的业务已经不需要去柜台。

**运营成本收入比**
> 意思：为了赚 100 块营业收入，要花掉多少运营成本。

本项目锚定值 **27.45%**。这个数字取自平安银行年报的公开披露，
是模拟数据里**唯一直接用真实值当锚点**的比率（其余用行业区间）。

**自贸区 / 自贸试验区分行**
"自由贸易试验区"是国家设立的、在关税和金融监管上有特殊政策的区域。
上海自贸区包含外高桥、临港新片区等片区。
**本项目的岗位（平安银行上海自贸分行运营培训生）就在这个体系里。**

### 1.2 数据分析术语

**指标**
可以被量化记录的一个数，比如"今天的柜面业务量 = 170 笔"。
反例："客户体验不错"不是指标，因为它没法量。

**基线**
> 意思：**"正常应该是多少"**，用来跟当天实际值比较的参照水平。

这是整个项目最核心的概念。**基线选错，后面全错。**
本项目的基线是"这家网点、这个星期几、过去几周的中位数"。

**中位数**
把一堆数字从小到大排队，站在正中间那个。
比平均值更稳——平均值的缺点是会被个别极端值带偏。

> 例子：5 个客户等候时长是 3、4、5、6、500 分钟。
> 平均值 = 103.6 分钟（完全不能代表实际情况），中位数 = 5 分钟（这才对）。

**异常 / 异常值 / 偏离度**
某天的数明显偏离基线。
`偏离度 = (当天值 − 基线) ÷ 基线`，结果是 +0.5 表示比基线高 50%。

**误报（假阳性）**
系统报了警，但实际上什么事都没有。

**漏报（假阴性）**
真的出了问题，但系统没报警。**漏报通常比误报更危险。**

**查全率（召回率）**
> 意思：**真的出问题的情况里，系统找出了多少比例。**

我埋了 7 个已知问题、找出 7 个，查全率 = 7 ÷ 7 = **100%**。

**注入异常（埋雷）**
> 意思：**我主动往数据里制造一个已知的问题，并登记下答案。**

这是本项目能自证清白的关键。做法是：
在 `data/raw/anomaly_ground_truth.json` 里写下"哪家网点、哪几天、我干了什么、应该表现成什么样"，
然后让检测程序去跑——**因为答案是我事先登记的，所以"找出几个""判断对不对"是可验证的，不是自说自话。**

**Ground truth（标准答案）**
即上面那份登记表。是所有评估的基础。

**阈值**
> 意思：**超过多少才算异常。**

比如规定"偏离 50% 以上才算"，那 50% 就是阈值。
**阈值定得太低会天天报警，定得太高会漏掉真问题。** 本项目所有阈值都在文档里公开写明。

**MAD（中位数绝对偏差）**
一种"这批数据正常波动有多大"的度量。
它和中位数一样对极端值不敏感——这是它相对标准差的最大优势（见 8.2 节）。

**EWMA（指数加权移动平均）**
一种侧重近期数据、同时保留部分历史记忆的平滑方法。
**它擅长发现"缓慢漂移"**——比如差错率每天高一点点，单看每天都不起眼，累积起来很严重。

**STL 分解 / 周期**
STL 是把一条时间曲线拆成"长期趋势 + 周期性波动 + 残余噪声"三部分的方法。

> **周期性为什么重要**：网点业务量一周一个循环，**周日大约只有工作日的三分之一**。
> 如果不把"星期几"这个规律剥掉，每个周日都会被误报成"业务量暴跌 65%"。

### 1.3 工程术语

**SQL**
一种用来向数据库提问的语言。比如"把每家网点上个月的平均等候时长算出来"。
本项目的指标层用 SQL 写成，共 **468 行**。

**数据库 / 表 / 字段**
数据库像一本账，**表**是其中一张工作表，**字段**是表里的一列。
本项目的明细表有 4 类字段组：标识（哪家网点哪天）、原始指标、派生比率、基线偏离。

**落库执行**
把写好的 SQL 真正放到数据库引擎里跑一遍。
**这一步很重要**：写出来的 SQL 和能跑通的 SQL 是两件事。
本项目第一次真正执行时，一次就跑出 **5 个真实缺陷**（见 16.4）。

## 二、我为什么做这个项目

### 2.1 从岗位要求反推

我在看平安银行上海自贸分行运营培训生这个岗位的描述时，把它拆成了三件事：

| 岗位要求 | 翻译成需要的能力 |
|---|---|
| "了解各项业务与产品、运营业务板块，熟悉相关业务流程" | 得**懂运营指标**到底是什么、意味着什么 |
| "树立风险合规意识" | 得能**分辨什么是真风险、什么是数据问题** |
| "精通银行全领域业务的综合金融业务精英" | 得能**从数据走到具体动作**，不是只交一张图 |

我原有的作品集偏互联网内容与用户分析，**缺一块银行运营的东西**，所以补了这个项目。

### 2.2 我的核心判断：难点不在"发现问题"

做一个"能报异常的看板"并不难——把阈值一设，超过就标红，一天能出几十条。

**难的是让人相信这些报警。** 而现实中，预警系统最常见的死法不是"漏报"，
而是**误报太多，业务人员干脆不看了**（这在运维和风控领域叫"告警疲劳"）。

所以我给自己定的目标不是"找出多少异常"，而是：

> **能不能把"不是问题的异常"也识别出来，并且说清楚为什么它不是问题。**

整份文档后面的技术选择，基本都是围绕这一条展开的。

## 三、一个与本岗位直接相关的真实发现

平安银行自 2022 年报起，**每一期定期报告都单独列示"上海自贸试验区分行"**。
我把 6 期数据都取了出来（这是真实公开数据）：

| 报告期 | 资产规模（亿元） | 员工人数（人） |
|---|---:|---:|
| 2022A（年报） | 685.12 | 159 |
| 2023H（半年报） | 837.82 | 157 |
| 2023A | 780.16 | 153 |
| 2024H | 828.51 | 157 |
| 2024A | 883.66 | 158 |
| 2025A | **1085.26** | **152** |

**四年资产增长 58.4%，员工从 159 人减到 152 人。**

这件事给了我做这个项目的具体问题意识：

> **当业务量在持续增长、而人手不增甚至减少时，运营管理靠什么？**

答案是三件事：
1. 把**单位产能**盯住（每个窗口、每个人能办多少）；
2. 把**窗口调度**做对（业务量涨了要加窗口，高峰期要弹性排班）；
3. 并且——**这点最容易被忽视**——**不要把系统的错误算到网点头上**。

后面整份文档的主线就是这个。

## 四、这个项目到底做了什么：七步流程

```
第 1 步  采集真实公开数据
        28 个来源、601 条已核实指标（人民银行 17 份报告 + 平安银行 6 份定期报告
        + 金融监管总局 + 中国银行业协会 + 上海市统计局）
            ↓  这一步的作用：知道"正常应该是什么量级"
            ↓  只取"比率类"参数当锚点，并且必须校验单位（见 7.3 的教训）
第 2 步  生成模拟数据
        20 家网点 × 90 天 = 1,800 条日运营记录
        等候时长用排队论公式推导、差错与投诉用泊松分布生成
            ↓
第 3 步  注入 7 个已知异常，并把答案登记到 ground truth
            ↓  ★ 质量闸门：如果注入的效果在数据里看不出来，程序直接报错退出
            ↓     （这道闸门救过我一次，见 11.1）
第 4 步  用 SQL 建模，算出监控需要的所有派生指标
        四层结构、468 行、5 张表，**已在数据库引擎里真正执行通过**
        核心产物：每家网点每天相对"同星期几基线"的偏离度
            ↓
第 5 步  三路异常检测（三套方法互相印证）
        MAD 横截面 + 单网点 EWMA 控制图 + STL 周期分解
            ↓
第 6 步  预警分级 + 成因判定
        分级 = 幅度 × 持续性 × 方法一致性
        成因 = 判定成"数据错误 / 口径差异 / 真实风险"三类
            ↓
第 7 步  产出交付物
        运营建议报告（Word）+ 交互式看板（离线网页）
        + Text-to-Excel Agent（可用自然语言提问的网页）
```

**每一步都有可检查的证据**：注入有自检报告、SQL 有执行日志、
检测有逐例评估表、网页 Agent 有 50 项自动化断言。

## 五、数据集说明书：里面到底有什么

### 5.1 网点构成（20 家）

**按类型：**

| 网点类型 | 家数 | 说明 |
|---|---:|---|
| 综合支行 | 12 | 业务最全，规模中等偏大 |
| 社区支行 | 4 | 规模小，主要服务周边居民 |
| 小微专营支行 | 2 | 专门服务小微企业 |
| 自贸区分行营业部 | 2 | 规模最大，业务最复杂 |

**按区域：** 浦东新区 4 家、闵行区 3 家、黄浦区 3 家、
静安区/宝山区/松江区/普陀区各 2 家、**自贸区临港新片区 2 家（SH010、SH011）**。

> **为什么要分类型**：不同类型网点的规模差好几倍。
> 拿社区支行跟自贸区分行营业部比"业务量高低"没有意义，
> 所以后面做异常检测时，**跨网点的比较只在同类型内部做**。

### 5.2 时间范围

**2026-06-22 ~ 2026-09-19，共 90 天**（约一个季度）。
选择 90 天是因为：够长，能看出趋势和缓慢漂移；又不会长到季节效应混进来。

### 5.3 数据长什么样：一天一条记录

## 六、指标体系：为什么是这四个维度

我没有把能算的指标都算上，而是按**运营管理的四个决策场景**分层，每层回答一个具体问题：

| 维度 | 回答什么问题 | 核心指标 |
|---|---|---|
| **效率** | 客户等多久？窗口够不够？ | 柜面业务量、平均/最长等候时长、窗口产能饱和度、单窗口业务量 |
| **服务** | 客户满意吗？渠道分流有效吗？ | 电子渠道分流率、智能设备占比、客户满意度、投诉率（每万笔） |
| **成本** | 单位业务的运营成本合理吗？ | 运营成本收入比、人均业务量 |
| **风险** | 操作合规吗？差错可控吗？ | 业务差错率、事后监督复核率、差错率周度趋势 |

**为什么是这四个，而不是别的？** 因为运营管理者每天要做的决策就这四类：
要不要加窗口（效率）、要不要做服务培训（服务）、
要不要优化排班控制成本（成本）、要不要做差错辅导或复核（风险）。

**指标要能指向动作，否则就是摆设。**

### 一条口径纪律

> **所有比率类指标，在数据层只存"分子"和"分母"，比率在查询时才计算。**

这是我在另一个项目里踩过坑之后定下来的规矩：
当时清洗层和分析层各写了一套分类词典，两套数永远对不上，排查了很久。

所以这次我在数据表里把**分子分母都留着**（比如差错笔数和业务量分开存），
下游想换口径可以自己重算，**不会出现"同一个指标有两个不同值"的情况。**

## 七、模拟数据是怎么造的

这一节回答："你凭什么说你的模拟数据是合理的？"

### 7.1 等候时长由排队论关系推导，而不是独立编一个数

最容易犯的错误是：给等候时长直接生成一串随机数。
**那样的话，"业务量高"和"等候时间长"之间就没有关系了**——而这恰恰是现实中最重要的关系。

我的做法是让等候时长由**窗口利用率和排队论**推导出来：

```
等候时长 ∝ 利用率 ÷ (1 − 利用率)^0.85
```

其中 `利用率 = 单窗口业务量 ÷ 理论单窗口产能`（就是前文说的产能饱和度）。

**这个公式的含义**：
- 利用率低（窗口空闲）时，等候时长很短；
- 利用率越接近 100%，**等候时长不是线性上升，而是急剧飙升**——
  这正是排队系统的真实特性：90% 忙和 95% 忙，客户感受差很多。

**所以我的数据里，"业务量涨 → 饱和度涨 → 等候时长非线性暴涨"这个链条是自然成立的。**
这也让"产能不足"这类真实风险能够被检测出来。

### 7.2 差错与投诉用泊松分布，而不是乘倍数

**差错和投诉是"低频计数事件"**——一天可能 0 笔、1 笔、偶尔 2 笔。

如果用"把昨天的值乘以 1.5 倍"这种方式制造异常，会得到 0.0、1.5、2.25 这种
不可能是真实笔数的值（笔数只能是整数）。

**这个指标有多稀少**：本项目的周度差错笔数中位数是 **3 笔**（日均业务量约 135 笔 × 7 天 ≈ 942 笔，
按 0.4% 的差错率算，一周也就三四笔）。所以"一周从 5 笔变 15 笔"这种量级，
在绝对数上只差 10 笔，但相对变化率是 +200%。

所以这两个指标用**泊松分布**生成——这是描述"稀有事件发生次数"的标准概率分布。

**为什么这件事重要**：泊松分布的特点是**方差不独立于均值**（均值是 1 时，波动也就是 1 的量级）。
这意味着"从 5 笔变 15 笔"在绝对量上只差 10 笔，
但如果用**相对变化率**衡量却是 +200%，看起来严重得多。

**这个特性后来直接决定了我的一条判定设计：低频指标必须用绝对增量判据。**（详见 9.1 节）

### 7.3 三道质量闸门（这一步救过我）

造完数据不等于可以用了。我设了三道自动检查，**任何一道不过，程序直接报错退出**，
而不是带着坏数据往下跑。

| 闸门 | 检查什么 | 为什么必要 |
|---|---|---|
| **注入效果自检** | 每个注入的异常，在数据里必须真的看得出来（效应量达标），且对照指标保持平稳 | 否则会出现"我以为埋了雷，其实没埋上"——这会让我后面的评估完全失真 |
| **单位校验** | 从公开数据取来的参数，单位必须是比例（`%` 或纯小数） | 我曾把"离柜交易总额 2626.80 万亿元"这个**绝对量**误当成比率参数，导致分流率被设成 0.86，注入几乎失效 |
| **合理性校验** | 常态网点的产能饱和度必须落在合理区间 | 我曾标定出一个"正常状态下就排 3.5 小时队"的网点，把 23 条预警污染成了误报 |

**第一道闸门的具体作用**：它会告诉我"这个注入的效应量是多少"。
比如我原本想让某个网点"投诉率升 6 倍"，闸门会算出：
该网点投诉基线接近 0，乘 6 之后的期望值仍然不足 1 笔，**泊松抽样长期取 0**——
也就是说这次注入**根本没发生**。没有这道闸门，我会以为埋了 7 个雷，其实只有 6 个。

## 八、异常检测：怎么找出"不对劲"

### 8.1 检测的基本思路

对**每一家网点、每一天、每一个指标**，都问三个问题：

1. **和同类型网点比，它今天在不在正常范围内？**（横截面）
2. **和它自己的历史比，它是不是在慢慢变差？**（时序）
3. **扣掉"星期几"这个规律之后，剩下的波动大不大？**（周期剥离）

三路方法各有盲区，**同时报警才更可信**，所以三路都做。

### 8.2 三路方法：各自负责什么

| 方法 | 抓什么 | 具体做法 | 阈值 |
|---|---|---|---|
| **MAD 横截面** | 突然的、离群的异常 | 同类型网点的中位数 ± 1.4826×MAD，算 z 分数 | \|z\| > 3 |
| **EWMA 控制图** | **缓慢漂移** | 单网点自身历史做指数加权，λ = 0.25 | \|z\| > 3.0 |
| **STL 周期分解** | 剥离周内效应后的残余 | STL(period=7, robust)，看残差 | 残差 z > 3.0 |

**为什么用 MAD，不用常见的"3 倍标准差"？**

因为真实运营数据里**本来就存在**极端值（设备故障、营销活动、系统故障）。
标准差的计算方式决定了它会被这些极端值"撑大"，
结果是**真正的异常反而落进了放宽后的 3σ 范围内，检测不到**。

MAD 对极端值不敏感，所以它是更稳的"正常波动范围"度量。

> **一句话**：用标准差，极端值会把自己藏起来；用 MAD，它藏不住。

**为什么还需要 EWMA？**

MAD 抓的是"某一天特别离谱"。但有一类问题**每天都不离谱，累积起来才严重**——
比如差错率从 0.30% 慢慢爬到 1.13%，每天只高一点点，单日都过不了阈值。
EWMA 因为记住历史、看重近期，能发现这种**缓慢漂移**。

**这个能力在项目里被真正用到了**：SH011 那个"新人轮换导致差错率上升"的注入，
就是 EWMA 先报出来的。

### 8.3 最关键的一处修正：基线必须按星期几对齐

**这是整个项目返工最多、也最值得讲的一处。**

**发现问题的过程：**

我第一版用"**前 7 日滚动均值**"做基线——就是拿最近 7 天的平均值当"正常水平"。
跑完发现：**每个周日都报警，说业务量暴跌约 65%。**

原因很简单：网点业务量一周一个循环，**周日大约只有工作日的三分之一**。
而"前 7 日滚动均值"里混了 6 个工作日，所以每个周日跟它比都显得很低。

**更严重的后果（这一点才是致命的）：**

为了压制这些每周固定出现的假异常，我给预警加了一道"持续性门槛"——
**要求异常必须连续出现几天才算数。**

结果这道门槛**把真实的缓慢异常也一起滤掉了**：
7 个注入的异常，**只检出 4 个**。

因为缓慢漂移类异常本来就是"每天高一点点"，
它既过不了单日阈值，又因为强度不够而积不满"持续性"要求，两头落空。

**修正方案**：基线改成"**同星期几的中位数**"——
周一跟历史上的周一比、周日跟历史上的周日比。

**效果**：假异常消失，7 个注入异常**全部检出**。

> **这一处的教训**：做异常检测之前，必须先把数据自身的固有规律搞清楚
> （周期、趋势、节假日）。
> **否则你不是在检测异常，你是在检测"星期几"。**

### 8.4 预警分级：不是所有异常都一样重要

报警太多会让人麻木，所以我把预警分成了 3 级，用三个因素相乘：

```
严重度 = 幅度 × 持续性 × 方法一致性
```

| 因素 | 含义 | 为什么算进去 |
|---|---|---|
| **幅度** | 偏离基线多少 | 偏离 5% 和偏离 300% 显然不是一回事 |
| **持续性** | 连续几天异常 | 单日尖峰可能是抽样噪声；连续 5 天就更可能是真的 |
| **方法一致性** | 三路方法里有几路同时报警 | 一路报警可能是碰巧；三路都报警可信度就高 |

**最终结果**：171 条预警里，**163 条是 1 级（轻微）、8 条是 2 级**。
分级让运营人员可以"只看 8 条"而不是淹没在 171 条里。

## 九、最有价值的部分：把"数据错误/口径差异/真实风险"分开

**这一节是整个项目我认为最有价值的部分。**

### 9.1 为什么这件事比"发现异常"更重要

**单一指标的跳变，本身完全无法判断性质。** 举三个真实的例子：

| 现象 | 可能是…… |
|---|---|
| 某网点等候时长从 9 分钟跳到 656 分钟 | ①叫号系统字段单位错了（把秒当分钟）②网点真的瘫痪了 |
| 某网点业务量掉了 35% | ①统计口径调整了（剔除了某类业务）②客户真的跑了 |
| 某网点业务量涨了 82% | ①核心系统批量任务重跑、重复计数 ②周边新楼盘交付、客户真的多了 |

**这三组的处置方向完全相反**：
前一种是"修系统 / 回算基线，**不要问责网点**"，
后一种是"**马上派人去解决**"。

> **如果分不清，预警系统就会天天让网点背锅。**
> 而一旦网点发现自己总是被冤枉，这套系统就再也推不动了。

### 9.2 五类异常，各自的"签名"是什么

我用"**专属特征**"来区分它们——就像医生靠不同症状组合区分病因：

| 性质 | 专属特征（判据） | 正确处置 |
|---|---|---|
| **数据错误·字段单位** | 等候时长放大 **8 倍以上**；**且业务量与差错率都正常** | 修系统，**不问责网点** |
| **数据错误·批量重跑** | 业务量虚高，**但成本收入比反而下降**（指标之间自相矛盾） | 查批量任务 |
| **口径差异** | 业务量**台阶式**下降，但**等候时长没有跟着降** | 回算基线 |
| **真实风险·产能不足** | 业务量与等候时长**同步持续**走高 | 弹性排班 / 增开窗口 / 客户分流 |
| **真实风险·渠道故障** | 电子渠道分流率**骤降**，同时柜面量与等候时长**同步上升** | 查设备，临时增开窗口 |
| **真实风险·操作风险** | 周度差错率**持续抬升**（含缓慢漂移） | 抽查差错明细，加强事后复核与新人辅导 |
| **真实风险·服务风险** | 投诉率**绝对**增加（每万笔多 3 笔以上） | 回溯投诉工单，定位服务触点 |

**几个判据背后的道理：**

- **"成本收入比反而下降"**：这个比率的分母就是业务量。
  业务量被虚高，比率自然被动下降。**指标之间的自相矛盾，是数据错误的典型特征。**
- **"等候时长没跟着降"**：如果客户真的变少了，等候时长必然会降。
  **等候时长不降而业务量降，说明是统计口径变了，不是经营变了。**
- **"绝对增加 3 笔而不是百分比"**：因为投诉基线常常是 0。
  0 → 2 笔的相对变化率是"无穷大"，这个数字没有意义（详见 9.3）。

### 9.3 为什么差错率必须按周看

差错是**低频计数事件**：一天办 130 笔业务，差错可能 0 笔或 1 笔。

假设某网点上周基线是 5 笔差错，这周是 15 笔：
- 按**相对变化率**看：+200%，看起来极其严重；
- 按**绝对增量**看：只多了 10 笔。

而按照泊松分布的性质，一个日均 130 笔业务的网点，
一周内差错从 5 笔波动到 15 笔，**在统计上并不罕见**。

**投诉率更极端**：基线常常是 0，相对变化率直接变成**无穷大**（0.0 → 2 笔）。

**所以我的判定规则里：差错率用"周度口径 + 绝对增量阈值"，
投诉率用"绝对增量（每万笔增加几笔）"，都不用相对变化率。**

### 9.4 规则的先后顺序就是优先级

我的判定规则是按固定顺序检查的，**先满足的先算**。**实际的顺序是这样的**：

```
1. 真实风险·渠道故障      ← 为什么排第一，见下
2. 数据错误·字段单位
3. 数据错误·批量重跑
4. 口径差异（台阶式下降 / 兜底）
5. 真实风险·产能不足
6. 真实风险·操作风险
7. 真实风险·服务风险
8. （都不满足）待定
```

**为什么"渠道故障"必须排在"字段单位错误"之前？**

因为**设备故障同样会让等候时长放大**（大约 1.35 倍）。
如果顺序反了，一次真实的渠道故障会被先判成"数据错误"，
然后被丢进"不用管"的桶里——**第一版正是这样把 `atm_outage` 判成了 `data_error`。**

所以判断顺序的核心原则是：
**先排除那些"会伪装成其他问题"的性质**，而不是按严重程度排。

**这个顺序设计的一个已知短板**（我如实写出来）：
`操作风险`（规则 6）与`服务风险`（规则 7）可能**同时**满足——
因为差错率上升会带动投诉率上升。

这时我的规则会先命中"服务风险"，**但正确的答案应该是"操作风险"**——
差错是先行指标，投诉是滞后的后果。

**实测结果**：SH011 这一例就判错了（3 大类对、细分类型错）。
修正方向应该是加"先行者归因"：看谁先动、谁幅度更大、谁更持续。
**我暂时没有改，因为这会动到核心判定逻辑，需要重新做全套评估。**

## 十、结果：到底跑出了什么

### 10.1 检出能力

| 指标 | 结果 |
|---|---|
| 埋入已知异常 | 7 例 |
| 检出 | **7 例（查全率 100%）** |
| 性质判定正确（3 大类：数据错误 / 口径差异 / 真实风险） | **7 例（100%）** |
| 性质判定正确（**细分类型**） | **6 例（85.7%）** |
| 报警总数 | 171 条 |
| 落在埋雷期间的报警 | 36 条 |
| 不在埋雷期间的报警 | 135 条，占全部网点日 **7.50%** |

### 10.2 为什么给两个准确率数字

评估程序先按 **3 大类**归并再比对（数据错误 / 口径差异 / 真实风险），
这个口径下是 **7/7**。若按**细分类型**严格比对，则有一例判错：

> `error_drift`（SH011 新人轮换致差错率漂移，实测差错率由约 **0.30% 升至 1.13%**）应判为「**操作风险**」，
> 实际在整个异常窗口内只产出过「**服务风险**」预警。
> 原因是该网点差错率与投诉率同时抬升，而判定规则中服务风险条件先满足，
> 首报按投诉归因，此后一直沿这条路走。

**大类没错、细类错了。只报 7/7 会掩盖这一点，所以两个数都列出来。**

### 10.3 "误报率 7.50%"这个数字怎么读

**它必须被理解成误报率的"上限"，而不是真实误报率。**

原因是：我只往数据里注入了 **7 个**已知异常。
但检测程序并不知道这一点——它会把所有偏离基线的波动都报出来，包括：
- 真实运营中正常存在的波动（营销活动、临时调休、季节性起伏）
- 我**没有登记**的其他小幅波动

**这些都被算进了"非注入期预警"里，所以这个比率必然偏高。**

正确的读法是：**"在最坏情况下（把所有非注入报警都当误报），误报率也只有 7.50%"。**

这个说明我写在 `results/analysis.json` 的 `false_alarm_note` 字段里，**跟着数据走，不只在文档里。**

### 10.4 报警的构成

| 疑似成因 | 条数 | 是否应问责网点 |
|---|---:|---|
| 待定 | 77 | 否（先核实） |
| 真实风险·操作风险 | 63 | **是** |
| 真实风险·服务风险 | 13 | **是** |
| 真实风险·产能不足 | 8 | **是** |
| 口径差异 | 5 | 否（应回算基线） |
| 真实风险·渠道故障 | 2 | **是** |
| 数据错误·批量重跑 | 2 | 否（应修系统） |
| 数据错误·字段单位 | 1 | 否（应修系统） |

**86 条真实风险 vs 3 条数据错误 + 5 条口径差异。**
这个拆分比"发现了几条异常"重要得多：
**预警系统的价值不在于报出异常，而在于判断出哪些异常不是风险。**

### 10.5 分级结果

| 严重度 | 条数 |
|---|---:|
| 1 级（轻微） | 163 |
| 2 级（较重） | 8 |

运营人员可以**只看那 8 条**，而不是淹没在 171 条里。

## 十一、四次自我纠错

这一节我写在结果后面，因为**我认为它比结果本身更值得看**。
四次都是我自己发现并修掉的，而且每一次都改变了最终数字。

### 纠错一："投诉率升 6 倍"这个注入从未发生

**我原本想做的**：让某网点投诉率上升 6 倍，验证检测器能否发现投诉异常。

**问题**：跑完发现该网点投诉均值**恒为 0**。

**原因**：该网点投诉基线接近 0，乘以 6 之后期望值仍然不足 1 笔，
而投诉是用泊松分布生成的——期望不足 1 笔时，抽样结果长期就是 0。
**所以这个注入根本没发生。**

**修正**：
1. 加了 `validate_injections()` 自检闸门，每次注入都必须验证"效应量可观测"；
2. 低频指标改用**绝对件数**表述异常（比如"每日新增 5~9 笔"），而不是乘倍数。

**教训**：**低频计数指标不能用倍率来表达异常强度。**

### 纠错二：周内效应把真异常挤掉了

**问题**：7 个注入异常只检出 4 个。

**原因**：基线用了"前 7 日滚动均值"，导致每个周日都产生假异常；
为了压制假异常而设的"持续性门槛"，把真实的缓慢异常也一起滤掉了。

**修正**：基线改为**同星期几中位数**。

**效果**：7 个全部检出。

**教训**：**先搞清数据的固有周期，再谈异常检测。**（详见 8.3 节）

### 纠错三：一个更隐蔽的锚点错误

**问题**：注入自检把"产能不足"标记为 FAIL，但数据看起来是正常的。

**原因**：我从公开数据里取参数时，把"**离柜交易总额 2626.80 万亿元**"这个**绝对量**
当成了"分流率"参数——因为字段名里都有"离柜"两个字。
结果分流率被设成了 0.86（86%），导致"渠道故障"这类注入几乎失效
（分流率已经这么高，掉一点也看不出来）。

**修正**：锚点取用时**校验单位**，只接受 `%` 或纯比例形式的值，绝对量一律拒绝。

**教训**：**字段名相似不代表是同一个东西。取参数必须校验量纲。**

### 纠错四：我造出了一个"长期超负荷"的网点

**问题**：收尾复核网点画像时发现，有一家"自贸区分行营业部"在**正常状态下**
（**没有注入任何异常**）窗口饱和度就到了 **124%**、日均等候 **215 分钟**。

**后果**：它连带污染了 **23 条误报**——检测器忠实报警了，但报警反映的是**错误的输入**。

**原因**：网点规模档位标定错误（把这家网点的业务量给得太高了）。

**修正**：
1. **重新标定网点规模档位**，使**各类型的最高峰日**窗口产能饱和度落在 **0.6~0.9**——
   常态网点不应该长期满负荷，只有注入了"产能不足"的网点才会被推到高位；
2. 把"字段单位"的判据从"纯相对倍数"改为"**绝对量级 + 相对倍数 + 跨网点比较**"三重条件。

**修正后的实测结果**：排除全部注入窗口后，常态产能饱和度**中位数 0.609**，
5% 分位 0.183、95% 分位 0.973（不同网点规模差异本来就大）。
没有再出现"正常状态就排 3.5 小时队"的网点。

**教训**：**先确认数据本身是合理的，再去评价模型好不好。**
如果只盯着"检出率 7/7"，是发现不了这个问题的——
因为检测器没报错，它只是忠实反映了错的输入。

> 这四条合起来是一句话：
> **一个自己不会检查自己的分析流程，产出的数字再漂亮也不可信。**

## 十二、Text-to-Excel Agent 是什么

### 12.1 它解决什么问题

看板只能讲**一个固定的故事**（我预先设计好的那几张图）。
但实际工作中，人总会临时冒出新问题："哪个网点等候最长？""8 月比 7 月怎么样？"

**Agent 就是用来回答当场冒出来的问题的。** 而且它的产出是**Excel 工作簿**——
因为在银行运营岗位，日常真正要交付的东西就是 Excel，不是查询结果。

### 12.2 它长什么样、怎么用

打开 `results/运营问数Agent.html`（**双击即可，不需要联网、不需要装任何东西**），
在页面里用中文提问，比如：

- "哪些网点等候时长最长"
- "周一到周日业务量怎么变化的"
- "8 月相比 7 月业务量有没有异常"
- "看一下 SH010 这个网点的详细情况"
- "这个项目一共报了多少条预警，都是什么性质"
- "数据里有多少可疑的单位错误记录"

**左边会逐步亮起 Agent 的工作流程，右边实时给出结果和可下载的 Excel。**

### 12.3 七个阶段：它到底做了什么

| 阶段 | 做什么 | 页面上能看到什么 |
|---|---|---|
| 1 意图识别 | 判断你想问什么 | 识别方式、识别理由、选定了哪个操作 |
| 2 操作选择 | **白名单校验** | 白名单规模、校验是否通过、参数模式 |
| 3 口径守卫 | 抽取参数并**按口径纪律自动纠正** | 抽取日志、最终参数、触发了哪条修正 |
| 4 执行引擎 | 在浏览器内计算 | 计算范围、产出工作表、行数、图表数 |
| 5 工作簿构建 | 生成 Excel 规格 | 文件名、工作表清单、格式、声明已写入 |
| 6 文件产出 | 现场构造 `.xlsx` 文件 | 文件大小、是否含宏、兼容性 |
| 7 结果与解读 | 渲染结果并给出业务解读 | 解读文本、总耗时、数据性质复述 |

### 12.4 一条关键的安全设计：不让大模型写代码

Agent 的结构是：

```
自然语言 → 意图识别 → 从白名单里选操作 + 填参数 → 受控执行
```

**大模型永远不生成可执行代码**，只能在 6 个预定义操作里选一个并填参数，
参数还会被逐项校验范围。

这样从**结构上**排除了代码注入与模型幻觉带来的风险——
这与"让模型自由写分析代码"是本质区别，**而且页面上把这一点直接写给使用者看。**

### 12.5 口径守卫：把"知识"变成"不能犯的错"

Agent 里有一条会**主动改写参数**并把理由展示给用户：

> 当你问"差错率的趋势"时，Agent 会自动把**日度**切换成**周度**，并提示：
> "差错是低频计数事件，日粒度信噪比过低，已切换为周度口径。"

**这是把口径知识从文档变成代码约束的例子**——不是提示模型"注意一下"，
而是**不让它犯错**。

### 12.6 两个 Excel 的分工（如实说明）

| 文件 | 谁生成的 | 能力 |
|---|---|---|
| 网页里下载的 `.xlsx` | 浏览器端 SheetJS | 数字格式、列宽、冻结表头；**不含图表** |
| `results/参考工作簿_网点运营总览.xlsx` | Python（openpyxl） | 含 **3 张真实图表** |

浏览器能做到的格式能力有边界，**页面上第 5 阶段直接把这条边界写给使用者看，不假装支持图表。**

## 十三、我知道的局限

1. **网点级微观数据无公开来源。** 我已尽力检索，**11 项指标确认不存在**，全部记为 null。
2. **模拟数据只锚定"量级与波动范围"**，网点级具体数字不可用于推断真实银行。
3. **7 个注入异常是我设计的**，比真实异常更干净、更典型。
   **查全率 100% 不代表真实场景表现。**
4. **检测阈值是在本数据集上调出来的**，存在过拟合风险。
5. **节假日效应未单独建模**，只处理了周内（星期几）效应。
6. **误报率 7.50% 是上限口径**（原因见 10.3）。
7. **一例成因细分类型误判**（SH011，见 9.4 与 10.2）。
8. **SQL 层与 Python 层的稳健离散度口径不完全一致**：
   MySQL/DuckDB 没有 `MEDIAN` 聚合函数，SQL 层用"平均绝对偏差"近似，
   Python 层用真正的 MAD。
9. **语义层存在两份定义**（Python 设计原件 + 浏览器 JS 实现），有漂移风险，
   已在 `ops_semantics.py` 中标注为已知技术债。
10. 人民银行报告 **2025Q1 起改版**，删除了"人均持有银行卡"等明细项。
    这是"不再披露"而非"数据缺失"，做长时序时处理方式不同。

## 十四、如果重做一次

1. **先写"判据字典"，再写检测代码。**
   这个项目里判据是边做边加的，导致规则顺序这种关键设计散落在代码里。
   如果先集中定义，会更容易复查。
2. **把周内效应之外的其他周期也建模**（节假日、月末月初、季度末）。
   月末冲存款、季末冲量是银行业非常显著的模式。
3. **给成因判定加"先行者归因"**，解决 9.4 那个短板：
   同一大类内多个症状并发时，看谁先动、谁幅度更大、谁更持续。
4. **误报率应该用真实场景数据测**，而不是靠"注入了几个"来倒推上限。
   这需要真实数据，本项目做不到，所以只能如实标注。
5. **把 SQL 层与 Python 层的检测口径统一**，避免同一套数据两个结论。

## 十六、工程上踩到的坑

这一节不影响结论，但都是真实发生过的、后来者会遇到的问题。

### 16.1 批处理文件里的中文会让 cmd 语法解析失败

`cmd.exe` 按**控制台代码页**解析 `.bat` 文件。中文注释/参数在部分机器上
会让语法解析直接失败，报 `'xx' is not recognized as an internal or external command`。
存成 GBK 也无效（因为本机 cmd 代码页不是 936）。

**解法**：`run_all.bat` 写成**纯 ASCII**，中文文档放在 `.md` 和 `.ps1` 里。

### 16.2 PowerShell 脚本必须带 BOM

Windows PowerShell 5.1 对**无 BOM** 的 `.ps1` 按系统 ANSI 代码页解析，
里面的中文会变成乱码，报 `Missing '=' operator after key in hash literal`。

**解法**：`run_all.ps1` 保存为 **UTF-8 with BOM**。

### 16.3 不要把中文文件名作为参数传给 Python

Windows 命令行的代码页转换会破坏参数，中文文件名会变成 `\ufffd`。

**解法**：让脚本自己按目录发现文件（见 `md2docx.py` 的 `--all` 模式）。

### 16.4 SQL 写出来 ≠ SQL 能跑

指标层 SQL 共 468 行，此前**从未在任何引擎里完整跑过**，只验证过等价逻辑。
补做"真正落库执行"这一步之后，**一次就跑出 5 个真实缺陷**：

| # | 缺陷 | 症状 |
|---|---|---|
| 1 | `dws` 层引用了差错**笔数**，但 `dwd` 层只算了差错**率**、没带笔数 | `no column named txn_error_cnt` |
| 2 | `ads` 层用了成本收入比的 7 日均值，`dws` 层没算这一列 | `no column named op_cost_ratio_ma7` |
| 3 | 某个中间表只选了主表字段，join 来的基线列**没被带出来** | `no column named vol_wd_base` |
| 4 | 周度差错基线用 21 日均值，**把当前周的数据也混进去了** | 基线被污染，误触发 427 行 |
| 5 | 差错用**相对变化率**判据 | 5 笔→15 笔被判 +200%，正常波动全量误报 |

**教训**：**"看起来对"和"跑得通"是两件事。**

### 16.5 关于执行引擎：为什么用 DuckDB 而不是 MySQL

原设计目标是 MySQL 8。实测本机**无法获取 MySQL/MariaDB 二进制**：
官方 CDN 的 TLS 被重置（HEAD 通但下载 0 字节）、
国内镜像只镜像 Linux 的 apt/yum 包、`winget` 需要管理员提权。

因此执行引擎改用 **DuckDB**（`pip install duckdb` 即可）。

**兼容性不是假设的，是逐项验证过的**：`verify_engine.py` 对照本项目 SQL 实际用到的
8 类语法结构逐项执行，**8/8 通过**（含窗口函数 `ROWS BETWEEN ... PRECEDING`、
多层 CTE、`CREATE TABLE AS WITH`、中文标识符）。

**MySQL 的 DDL 文件保留**作为建模参考与生产目标；
`load_to_db.py` 内置一个方言翻译层（类型映射 + 剥离 `ENGINE=` / `CHARSET=` / `COMMENT`）。

### 16.6 一个必须说明的数字差异：SQL 层 942 条 vs Python 层 171 条

| 层 | 报警条数 | 基线口径 |
|---|---:|---|
| SQL 层（`ads_ops_alert`） | 942 | 同星期几**均值** + 绝对增量判据 |
| Python 层（`02_预警清单.csv`） | **171** | 同星期几**中位数** + 三路检测 + 持续性分级 |

**这个差距本身是有信息的**：它说明「基线口径 + 判据设计」比「SQL 写得对不对」
更决定预警系统能不能用——同一份数据，仅这两处设计差异就带来 **5.5 倍**的假信号量。

**分工因此明确**：SQL 层展示建模与窗口函数能力，**检测质量与最终结论以 Python 层为准**。

### 16.7 打包网页时的两个隐蔽陷阱

把多行 JavaScript 拼成一行内联进 HTML 时：

1. **`//` 单行注释会吃掉后面所有代码**（包括函数的收尾括号），
   导致整块脚本报 `Unexpected end of input`。**必须用 `/* */`。**
2. **数据里的 `</script>` 序列会提前闭合脚本标签**。
   内联 base64 数据时必须把 `</` 转义成 `<\/`。

### 16.8 Word 表格会撑出版心宽度

`python-docx` 生成表格时如果不显式设置总宽和单元格边距，
表格在 Word 里会超出页面宽度。需要同时设置 `_tbl_width()` 与
`_tbl_cell_margins()`（本项目用了 left=60, right=60）。
